<Example name="basic" both />

AppKit's `NSSearchField` as it appears in a toolbar: the same bezel as a
[Toolbar Button](/components/toolbar-button) around a native `<input type="search">`. Base UI
has no search field; inside a [Toolbar](/components/toolbar) the input is Base UI's Toolbar
Input, so it joins the toolbar's keyboard navigation.

## Usage

```tsx
import { ToolbarSearchField } from "macalicious/toolbar-search-field";
import "macalicious/toolbar-search-field.css";

<ToolbarSearchField style={{ width: 240 }} onValueChange={setQuery} />
```

Native input props go to the input, so `value`, `defaultValue`, `onChange`, `name`, `disabled`
and `aria-*` work as on an input. The exceptions: `className`, `style` and `ref` belong to the
root element; `inputRef` reaches the input, to focus it from a Command-F handler;
`onValueChange` and `clearLabel` are the component's own; and the preview attribute
`data-force` lands on the root, which draws the focus ring.

<Example name="controlled" />

### Tokens

`tokens` puts search tokens before the text, as Finder does when a search is narrowed to a
criterion: pass `ToolbarSearchFieldToken`s, whose children are the value and whose `criterion`
is the part before it, in small capitals with a chevron. The field shows them and does not
keep them: add one from your `onKeyDown` (Return, in the example), remove the last on Delete
in an empty field, and remove them all in `onClear`, which the clear button and Escape call.
While there are tokens the placeholder is not shown and the clear button is.

<Example name="tokens" both />

### Search menu

Font Book's field has a small chevron beside the magnifier: the two are a button that opens
the field's search menu, a choice of what is searched. Pass a `ToolbarSearchFieldMenuButton`
as `searchMenu` and make it the trigger of a [Menu](/components/menu). The field places the
button where the magnifier was and starts its text 4 pt later; the menu, and what a choice
does, are the application's.

## Guidelines

Not verified: this section paraphrases Apple's Human Interface Guidelines and was not checked
against Apple's text.

- Put the field at the trailing edge of the toolbar, after flexible space.
- Start searching as people type when results are cheap, or on Return when they are not.
- Keep the placeholder short: "Search". It is also the field's accessible name unless you give
  an `aria-label`.
- When search can be narrowed, show a [Scope Bar](/components/scope-bar) under the toolbar.

## Variants and states

<Example name="states" both hideCode />

| State | How it is triggered | Look |
| --- | --- | --- |
| Empty | no text | Magnifier and placeholder; no clear button |
| With text | text in the input | Clear button, 14 pt, at the trailing edge |
| With tokens | `tokens` | 15 pt capsules 26 pt from the fill's edge, the insertion point 3 pt after the last; clear button; no placeholder |
| Read-only | `readOnly` | No clear button, also with text; the text cannot be cleared |
| Focused | focus in the field | Ring 3 pt outside the fill, over the border, which shows through it, and a hairline inside the fill; the typed text in the label colour; key window only |
| Disabled | `disabled` | Dimmed glyph and text (provisional) |
| Inactive window | `data-window-state="inactive"` on an ancestor | Flat outlined bezel (provisional) |

| Variant | Look | Seen in |
| --- | --- | --- |
| `standard` (default) | In Dark Aqua a translucent fill, white at 22.5% | Finder, Font Book, Keychain Access, Notes, System Preferences and every other dark toolbar but one |
| `bright` | In Dark Aqua white at 33.6%, with a lighter placeholder; the same as `standard` in Aqua | Console |

<Example name="bright" both hideCode />

The field has no intrinsic width worth keeping: set `width` in `style`. The screenshots show
160 pt (System Preferences), 238 pt (Preview) and 323 pt (Finder, Help).

## Sizes

One size: the field is 22 pt high and at least 60 pt wide. It has no width of its own, so set
one with `style` or let a flexible toolbar space size it.

## Accessibility

- A native search input, named by its placeholder unless `aria-label` or `aria-labelledby` is
  given; a field with `placeholder=""` shows no placeholder text and needs one of the two. Wrap the toolbar or the field in an element with `role="search"` when it searches the
  whole window.
- Escape clears the text; a second Escape, in an empty field, gives up focus. A `readOnly`
  field is not cleared: Escape gives up focus at once. Return is left to your `onKeyDown` or
  to a surrounding form.
- The clear button is a real button with the name "Clear" (`clearLabel`). It is out of the tab
  order, because Escape does the same from the keyboard, and it returns focus to the input.
- The focus ring shows only in the key window.
- Inside a `Toolbar`, moving focus to the field with the keyboard selects its text and a click
  places the caret, as in AppKit.
- Tokens are text before the input, not controls: the input is described by them
  (`aria-describedby`), so a screen reader announces “Name report” with the field. They are
  removed from the keyboard with Escape, or with whatever your `onKeyDown` does on Delete.
  The pull-down menu that Finder opens from a token's criterion is not part of this
  component.
- The search menu button is a real button and needs an `aria-label` that says what its menu
  chooses ("Search in"). Inside a `Toolbar` it is reached with the arrow keys, before the
  input; on its own it is a tab stop before the input. A click on it does not move the caret
  into the field. While it has the keyboard focus the field shows its focus ring. A disabled
  field disables the button, so its menu cannot be opened; the button can also be disabled on
  its own.
