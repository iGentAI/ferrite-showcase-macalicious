# Catalina token sheet

Generated by `tools/build.py tokens` from `tokens-core.txt` (the curated core, edit that file), this
introduction (`tokens-intro.md`) and the token tables in `handoff/*.md`. Machine-readable form:
`tokens.json`.

## How to read this sheet

- **It maps onto the library's token layer.** Token names are the CSS custom properties in
  `src/styles/tokens/{color,accent,typography,metrics,controls,elevation,materials}.css`. The
  "In scaffold" column says whether the name already exists there (`yes`) or is proposed (`new`).
  A name written `--mac-accent-light[purple]` is the value of `--mac-accent-light` inside the
  `[data-accent="purple"]` rule. Appearance-dependent tokens are written once in the scaffold as
  `light-dark(<light>, <dark>)`; the two columns here are those two arguments.
- **Colour values are CSS-ready sRGB.** The reference PNGs store panel values in a Display P3-like
  space; each chromatic colour was converted through the embedded ICC profile. Where the stored
  pixel value differs it is shown in brackets so that `tools/measure.py at` reproduces it. Greys are
  the same in both. The conversion is validated by the accent swatches: the measured stored values
  convert to within one or two levels of Apple's published catalog colours (blue `#007aff`, purple
  `#953d96`, pink `#f74f9e`, red `#e0383e`, orange `#f7821b`, yellow `#fcb827`, green `#62ba46`).
- **Tags** are the provenance tags of `CONVENTIONS.md`: [M] measured, [C] computed from measured
  values (alphas recovered from composites, fitted shadows, font sizes from cap heights),
  [D] documentation, [I] inferred. Evidence names the component spec that holds the pixel citations
  (filenames omit `10-15-Catalina-` and `.png`).
- **Translucent values** (`rgba()`) were recovered from opaque composites over known backgrounds.
  The composite that was measured is given in the evidence, so a build can check itself against the
  same background.
- **Dark greys vary by a few levels between screenshots** because Catalina tints dark window
  backgrounds with the desktop picture ("desktop tinting"; off with the graphite accent). The sheet
  gives the untinted value as the token and the tinted range in the note.

## Notes from adopting the sheet in the token layer

The token-layer thread adopted this sheet in `src/styles/tokens/` and reported where a value needed a
different form in CSS. The sheet now carries these forms; the points worth knowing:

- **Stacked shadows and highlights.** A measured row is a composite. When two CSS layers overlap on the
  same row their alphas combine, so `--mac-bezel-highlight` and `--mac-bezel-shadow` list per-layer
  alphas that composite to the measured rows, not the measured row strengths themselves.
- **Alignment rectangles.** The library's control boxes are AppKit alignment rectangles, 0.5 pt larger
  than the visible bezel on each side. Spacing tokens are therefore the alignment distances (12 px
  between buttons, 20 px window margin); the visible distances measured in the screenshots are 13 pt
  and 20.5 pt and are given in the notes.
- **Control radius: measured 3.75 pt, token `3.5px`.** 4 pt is AppKit's nominal radius but not what is
  drawn. The measurement in this spec is unchanged: a least-squares fit of a rendered 1 px ring to the
  14 x 14 px corner crops gives 3.75 pt on the outer edge of the 0.5 pt border [C]
  (`components/push-button.md`). The token holds `3.5px` by product decision (2026-10-02). That is an
  implementation choice, tagged [I] in the table, not a new measurement. Its basis is the token layer
  owner's comparison, recorded in `src/styles/tokens/metrics.css` and not re-run for this sheet: as a
  CSS `border-radius` on the bezel's outer edge, rendered in Chromium and compared with the eight
  push-button bezel crops at 2x, the summed mismatch is 0.28 points at `3.5px`, 0.39 at `3.625px`,
  0.98 at `3.75px` and 1.61 at `4px`. The two figures are not the same quantity, and the quarter point
  between them is inside the uncertainty of both. The likely reasons, none of them established [I]:
  - *Scale.* The captures are 2x, so 0.25 pt is half a device pixel. The fit separates 3.75 from 3.5
    by about one level of rms error (1.5 against 2.7), which is the size of the dither noise in a
    flat fill.
  - *Coordinates.* The radius depends on which edge it is attributed to: the same corner is 3.25 pt on
    the fill, 3.5 pt on the centre line of the border, 3.75 pt on its outer edge and 4.25 pt on the
    halo. A half-device-pixel difference in where the fitted ring and the CSS border box sit
    relative to the pixel grid is therefore a 0.25 pt difference in radius.
  - *Rasteriser.* The fit used this project's own ring renderer and the comparison used Chromium's;
    neither is Core Graphics, each anti-aliases a small arc differently, and AppKit's corner need not
    be a circular arc.

  Cite 3.75 pt for what Catalina draws under the fit's definition, build with `3.5px`, and never use 4,
  which both the fit and the comparison exclude.
- **Radii re-fitted on 2026-10-02.** `tools/corner_fit.py` renders a corner at each candidate radius
  and reports the rms difference from the stored pixels; it reproduces the push-button fit (3.75 pt on
  the border, 4.25 pt on the halo). Run on values that build threads questioned, it moved three radii
  that had been read off a pixel grid: the box and `--mac-radius-group` from 2.5 to 4 pt, the Disk
  Utility capacity bar from 3.5 to 5 pt, and the tab strip from 3 to 3.5 pt. The 4 and the 5 are the
  values to build with: the box fits 3.875 in light and 4 in dark, the bar 4.75 to 5.125 by end and
  appearance, so 4 in light and 5 are rounded values, tagged [I] in their rows since 2026-10-03. In each case the last
  blended pixel of the arc had been taken for the straight edge. The token layer took
  `--mac-radius-group: 4px` in pull request #12 (commit `1e61ce54`, merged as `f7bf6ac1`); it held
  2.5px from the earlier reading until then.
- **Second round of fits, 2026-10-02.** Sixteen more values were fitted, on thirteen controls and one
  app blueprint (commands and results in `handoff/components-remeasure.md`). Confirmed: checkbox 3, token 2. The
  window's top corners fit 5, as the grid reading has it, and its bottom corners 5.125, both on the
  alpha channel of the window capture and both coarse (the shadow outside the corner is not flat),
  so the window fit is an estimate and not a confirmation. Moved: pop-up button and segmented control
  4 to 3.75 (the push-button bezel), toolbar button and toolbar search field 4 to 4.25, the Automator
  search field 2.5 to 4.25, the Music sidebar search field 3.5 to 3.75, stepper 5.5 to 5.125 to 5.25,
  preferences-toolbar selection 3.5 to 4, image well 5.5 to 6.5, the Music display panel 2 to 2.625
  (2.5 to build with).
  None of these changes a numeric value of a core CSS token (the `--mac-*` tables of this sheet):
  the push-button family is covered by the adopted control radius above, and the others are
  component values. The provenance of two
  core tokens did change: `--mac-radius-checkbox` keeps 3px and is now tagged [C] with the fit as
  evidence and note; `--mac-radius-window` keeps 5px, was tagged [C] by that round and is tagged [I]
  since 2026-10-03, because one value for four corners whose fits give 5 and 5.125 is a choice (its
  note gives both fits). The family token candidates did change in value:
  the rows of `handoff/<family>.md` (and of `tokens.json`, `family`) that repeat a
  component radius were brought up to the fitted values on 2026-10-03. A build thread that used the earlier
  figure (the fields-and-labels batch built the small search field at 3.5) should compare against
  the fitted one.
  **Still not fitted:** every radius of a surface that lies on the wallpaper or on a translucent
  material in a full-screen capture, where the background is not flat and the tool's model does not
  apply (menu, popover, notification, Spotlight, Dock, HUD, app switcher, Launchpad, Siri, login
  window, Notification Center cards and the switch drawn on them), plus the small and mini sizes of
  controls (two small controls are fitted: the push button, 3.75, and the Automator search field,
  4.25) and the artwork
  radii in the app blueprints. Treat an unfitted radius as good to about 1 pt.
- **Third round of fits, 2026-10-03.** The radii the second round left on flat backgrounds were
  fitted (commands and results in `handoff/components-remeasure.md`). Moved: scope-bar on pill from an
  inferred "about 4, fully rounded" to 3.75 (a rounded rectangle, not a capsule; fitted in Finder
  light and dark and in light Preview; dark Preview is not flat, so it is inferred from those three),
  colour-swatch and appearance-thumbnail selection ring 5.5 to 6 on the outer edge (three captures),
  focus ring around a square control 2.5..3 to 3.25. New: the toolbar button in dark fits 3.75 on its
  border-less fill, the same shape as the light fill inside the 4.25 pt border. Fitted: the focus
  ring around the 4.25 pt toolbar search field is 6.75. That is the control radius + 2.5, and the
  rule "control radius + 2.5" for other rounded controls is a generalisation from this one fit,
  tagged [I] (it was called confirmed here until 2026-10-03). Not fitted after all: the switch track lies on the Notification Center material, which is
  not flat, so its 10.5 pt remains half the measured height and two trial fits are recorded as
  invalid. The image corner inside the thumbnail selection ring is a grid reading of 4.5 to 5, with
  4.5 to build with tagged [I]. None of these is a core CSS token of this sheet; they are component
  values, and the family token candidates that repeat them changed with them (scope-bar pill,
  thumbnail ring and image radius).
- **Toolbar bezels fitted on their own corners, 2026-10-03.** The toolbar segmented control, the
  toolbar pop-up and the smart search field had taken 4.25 for both appearances from the toolbar
  button or the toolbar search field, tagged [I]. Each is now fitted on one corner of its own in
  light and in dark: 4.25 on the outer edge of the light 0.5 pt border, 3.75 on the edge of the dark
  fill, which has no border. The segmented control's dark fit has its optimum at 3.625 with 3.75
  nearly as good (rms 1.46 against 1.53), so its computed value is 3.625 and the 3.75 to build with
  is tagged [I]. The
  toolbar search field in dark fits 3.75 and the preferences-toolbar selection in dark 4. The
  toolbar bezel radii, 4.25 and 3.75, describe one shape: a 3.75 pt fill with or without a 0.5 pt
  border outside it. None of the radii in this paragraph is a core CSS token of this sheet; the
  family token candidates that repeat them changed with them.
- **Further fits and rounded values, 2026-10-03.** A default button was fitted for the first time
  (3.5 on the border, coarse because its fill is a gradient; its row had rested on a pop-up button's
  accent cap, and that it shares the push button's 3.75 outline is tagged [I]). The dark display
  panels were fitted: Music 2.5 to 2.625, as in light; Podcasts 2.75 at its one fittable corner,
  against 1.875 in the light capture, a difference that is recorded as an open observation and not
  explained: the dark Podcasts radius is not a resolved value. Where a row
  led with a rounded value as if it were the fit (the box's 4 in light, the Disk Utility bar's 5),
  the fitted optima now stand in the [C] row and the value to build with is a separate [I] row;
  `--mac-radius-group` keeps 4px and is tagged [C] in dark and [I] in light. That is the one core
  CSS token this paragraph touches, and its value does not change; the default-button, display-panel
  and capacity-bar radii are component values, and the family token candidates that repeat them
  changed with them.
- **Mini control radius.** No screenshot shows a mini bezel. The token layer uses a provisional 2.5px
  and this sheet proposed 3px; both are inferences with no pixel basis, so the sheet now gives the
  token layer's 2.5px, tagged [I], and records the earlier 3px in the row's note.
- **Dither tolerance.** Flat fills in the captures carry about one level of noise per channel, so two
  samples of the same colour can differ by one or two levels. The accent swatches in the core table
  (unselected swatch) and in the accent matrix (selected swatch) differ this way for pink, red, yellow
  and graphite; use the core table. `--mac-accent-bezel-top` light reads `#6ca5fb` or `#6ca6fb`
  depending on the pixel.
- **Documented values are not converted.** Tokens tagged [D] are Apple's published sRGB numbers and are
  shown as published.
- **Tracking** stays `normal` on Apple platforms; the three tracking values apply only with the
  fallback font.
